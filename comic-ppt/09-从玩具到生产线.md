### 画面与版式硬性规则（防低质的关键）
1. **角色不超过单页画面的 1/3**，禁止大头像特写撑满页面；角色只在剧情页和对话气泡旁出现，且为全身或半身场景化姿态（坐着敲代码、站在白板前、围着工位）。
2. **每页 3-6 个信息块**，正文文字每页不超过 120 字，对话气泡每句不超过 20 字。
3. **禁止呆板的横竖四宫格/六宫格均分布局**。每页从以下版式库中选择：对角线分割、斜切面板、杂志式不对称网格、左侧竖栏导航 + 右侧主视觉、出血大图 + 浮动文字卡片、跨页式横向时间轴、中心辐射图、Z 字形阅读动线。

6. 代码/伪代码用**深色终端卡片**，带行号和语法高亮，卡片一角可以有迷你角色注释气泡。
7. 每页保留一个「视觉钩子」：一道斜切色块、一个出血的道具、一条贯穿页面的虚线动线，制造冲击力。

## 【本集设定】

- **本集目标（大结局）**：把前八集的能力收拢成「如何接入真实企业系统」——ACP / JSON-RPC SDK / Python SDK 三种自动化入口、可运行的 examples、以及支撑这一切的工程纪律；最后以老师视角给出采用路线图与风险清单。
- **研发收获**：分清 ACP（automation-only）与 SDK（完整事件流）两条协议通道的适用场景；知道用哪个 example 起步；理解快照测试、覆盖率门槛、Agent Notes 这套工程文化的含义。
- **领导收获**：拿到一份可直接使用的三阶段落地路线图与一页风险清单（开发者预览定位、破坏性变更、密钥管理、vm 边界）——本集是决策者的「带走页」合集。
- **故事梗概**：季度评审会。老师召集全员：「demo 很好，但我要它接进 CI、接进 IDE、接进数据平台——而且我要知道风险。」大雄主讲接入方案，出木杉讲工程纪律，胖虎负责安全质询，静香验收体验。散会时，哆啦A梦悄悄把一张「22 世纪架构师结业证书」放在大雄桌上。
- **出场角色**：全员（大雄、哆啦A梦、老师、出木杉、胖虎、静香、小夫）
- **结尾**：系列收官，附「继续深入」资源索引。

### 第 3 页 ｜ 概念页：三条接入通道
- **版式**：中心辐射图。中心是 dsh 内核发光体，三条车道向外辐射，宽度和颜色不同。
- **画面**：车道一「headless CLI」（窄而快，直通 CI 机房）；车道二「ACP」（标准轨，通向 IDE 大楼）；车道三「JSON-RPC SDK」（双向八车道，通向企业数据平台）。大雄站在三岔口当交警。
- **文字**：
  - 标题：同一个内核，三种方向盘
  - 车道标注：
    - **Headless**：`pnpm dsh --profile headless "任务"`——一次性运行器，无服务器，CI 友好
    - **ACP（Agent Client Protocol）**：JSON-RPC over stdio，自动化专用——`session/new`、`prompt`、`cancel`、`permission`
    - **SDK**：自研 newline JSON-RPC + TypeScript / Python 客户端——完整 session 事件流
  - 底部一行：三者共享同一套模型、会话与插件生态——差别只在「门」，不在「屋子」。
- **技术点**：ACP 见 `packages/acp/acp/`；SDK 见 `packages/sdk/`（protocol + server + client）与 `python/`（Python SDK）。

### 第 4 页 ｜ 深度页：ACP vs SDK —— 选哪条车道
- **版式**：对角线分割对比。左上 ACP（标准协议徽章，对接 IDE 图标）；右下 SDK（完整事件流的宽幅光带）。
- **画面**：左上小夫举着 IDE 徽章炫耀「标准协议」；右下出木杉面前的屏幕上事件流如瀑布滚动。
- **文字**：
  - 标题：两条协议通道的分工
  - 左上标注（ACP）：
    - 定位：automation-only——给 IDE 和父 agent 用的标准协议
    - 输出：仅已提交的 assistant 文本块（精简、稳定）
    - 额外彩蛋：`subagent-acp` 让 dsh 也能当别人的 ACP 客户端（第 7 集的委派）
  - 右下标注（SDK）：
    - 定位：完整运行时驱动——initialize、session/prompt、shutdown + 推送 `session.event` / `subagent.*`
    - 输出：全量 session 事件流——审计、计费、自定义 UI 都靠它
  - 气泡（小夫）：标准协议才是正道！
  - 气泡（出木杉）：标准解决「接得上」，全量事件解决「看得见」——用途不同，不是优劣。
- **技术点**：ACP 是面向自动化的标准协议（IDE/父 agent 场景）；SDK 暴露完整事件流；两者是 transport 而非能力缝。

## 【本集技术检查单】（供校对，非页面内容）

- [ ] 三条接入通道：headless（`pnpm dsh --profile headless`，一次性、无服务器）/ ACP（JSON-RPC stdio，automation-only：`session/new`、`prompt`、`cancel`、`permission`，仅输出已提交 assistant 文本块）/ SDK（newline JSON-RPC，`protocol`+`server`+`client`，完整事件流，含 Python SDK）
- [ ] examples：`examples/acp-agent/`（demo:acp）、`examples/headless-agent/`（含 e2b/advanced 变体）、`examples/jsonrpc-agent/`（含 minimal.cordis.yml）、`examples/web-cordis/`（demo:cordis）
- [ ] 凭据：`packages/credentials/`，`DEEPSEEK_API_KEY` 经环境变量/`.env`，永不入库；CI 无密钥时 e2e 自跳过
- [ ] 工程门禁：`test:coverage`（per-file 100%）、`test:snapshot`（无密钥回放）、`doc-sync`、`hygiene`、`duplication`、`typecheck`、`lint`；非平凡改动须附 Agent Note
- [ ] 生态：GitHub topic `dsh-plugin`、Discussions、Discord；MIT 协议
- [ ] 风险项：开发者预览（破坏性变更明示）、`SESSION_FORMAT_VERSION = 0`、外部 API 依赖、自修改/高权限的边界
- [ ] ACP/SDK 是 transport 而非能力缝；`subagent-acp` 复用 ACP 作为委派 Provider
