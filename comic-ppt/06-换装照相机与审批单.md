### 画面与版式硬性规则（防低质的关键）
1. **角色不超过单页画面的 1/3**，禁止大头像特写撑满页面；角色只在剧情页和对话气泡旁出现，且为全身或半身场景化姿态（坐着敲代码、站在白板前、围着工位）。
2. **每页 3-6 个信息块**，正文文字每页不超过 120 字，对话气泡每句不超过 20 字。
3. **禁止呆板的横竖四宫格/六宫格均分布局**。每页从以下版式库中选择：对角线分割、斜切面板、杂志式不对称网格、左侧竖栏导航 + 右侧主视觉、出血大图 + 浮动文字卡片、跨页式横向时间轴、中心辐射图、Z 字形阅读动线。
4. **禁止「一页一张大插图 + 底部一大段文字」的小人书版式**。信息必须以标题、要点列表、标注引线、迷你图表的结构化方式呈现。

6. 代码/伪代码用**深色终端卡片**，带行号和语法高亮，卡片一角可以有迷你角色注释气泡。
7. 每页保留一个「视觉钩子」：一道斜切色块、一个出血的道具、一条贯穿页面的虚线动线，制造冲击力。
8. 文字用中文，术语保留英文原词（如 profile、preset、approval）。

## 【本集设定】

- **本集目标**：讲清 dsh 的配置组合体系（profile / bundle / patch 四层叠加）与 per-session 的 preset 机制，以及权限预设与审批策略如何构成企业级治理面。
- **研发收获**：理解启动时插件树如何按层叠加；`dsh-base` / `dsh-web-app` / `dsh-headless` 的分工；preset 在 agent 创建时挂载的隔离语义；`!!js` 表达式与 overlay 的使用边界。
- **领导收获**：同一套内核如何通过「换装」产出面向人类工作台、CI 自动化、IDE 集成的不同产品形态；权限与审批的 fail-closed 设计如何让「默认安全」成为出厂配置。本集老师戏份最重。
- **故事梗概**：公司要同时上线三种用法：研发日常用的 Web 工作台、CI 流水线上的 headless 质检 agent、以及给外包团队用的「受限版」。大雄以为要维护三套代码，哆啦A梦拿出「换装照相机」——同一个内核，换三套装备。胖虎试图给自己申请 `danger-full-access` 权限，被老师的审批单体系当场打回。
- **出场角色**：大雄、哆啦A梦、老师、胖虎、出木杉、静香
- **结尾钩子**：大雄遇到新麻烦：一个任务太大，一个 agent 干不完，能不能「摇人」？→ 引出下集 subagent 与沙箱。

### 第 4 页 ｜ 概念页：profile、bundle、patch 各是什么
- **版式**：中心辐射图。中心是「cordis.yml」发光文档，三条引线连出三个角色卡。
- **画面**：三张角色卡如道具图鉴：profile 是「衣柜」（具名套装，存在 Harness home）、bundle 是「可快递的装备包」（npm 包，带 `dsh.bundle` 标记）、patch 是「修改贴纸」（按 id 覆盖）。哆啦A梦把三张卡别在口袋上。
- **文字**：
  - 标题：组合艺术的三种材料
  - 卡片标注：
    - **Profile**：具名组合（`web` / `headless` 是官方模板），列出自己叠放的 bundle
    - **Bundle**：可分发的插件组合包——代码 + 配置行，npm 安装即用
    - **Patch**：按 `id` 精确修改既有配置，支持 `!!js` 表达式做条件逻辑
  - 气泡（出木杉，画外音）：注意边界——`!!js` 只允许出现在插件 config 和 `disabled` 字段，其他元数据必须保持字面值。
- **技术点**：`!!js`（注意不是 `!js`）的合法位置由 loader 规则限定；条件组合也可以用 overlay 达成（`docs/cordis-primer.md`）。

### 第 5 页 ｜ 深度页：preset —— 给单个 agent 换装
- **版式**：杂志式不对称网格。左侧 3/5 是「特工装备间」等距图：不同的 agent 小人排队领取各自的任务装备包；右侧 2/5 深色代码/配置卡片。
- **画面**：每个 agent 小人领到不同的 preset 背包：「代码审查员」「数据分析师」「只读顾问」；装备间的每个柜子有隔离玻璃（isolate realm 的视觉隐喻）。
- **文字**：
  - 标题：profile 管进程，preset 管单个 agent
  - 配置卡片：
    ```yaml
    # presets/reviewer/cordis.yml（节选）
    - name: reviewer-tools
    - name: reviewer-persona
    ```
  - 要点：
    - preset = 每个 agent 会话自己的 `cordis.yml` 组合
    - 挂载时机：agent 创建时的 `setup(agentCtx)`——失败则整次创建回滚
    - 隔离红线：preset 内的服务必须带 `isolate` realm，禁止泄漏到进程全局
    - 切换会落日志：`agent-preset/selected` 事件

- **技术点**：preset 机制见 `packages/preset/agent-presets/`（`mountPreset`、`discoverPresets`、`resolveSessionPreset`）；重建会话时必须经 `resolveSessionPreset()` 而非只读 header。

### 第 7 页 ｜ 深度页：approval —— 默认安全的设计
- **版式**：左侧竖栏（竖排「fail-closed」+ 安全条纹），右侧主视觉：一座「审批灯塔」——策略光源照亮三条航道。
- **画面**：灯塔三束光分别照向三条航道：`ask`（默认航道，通向人类审批席）、`never`（封闭航道，直接拒绝）、以及一条暗礁航道（无任何 answerer 时 → 自动落到 `unavailable`，闸门关闭）。
- **文字**：
  - 标题：没人值班的时候，闸门保持关闭
  - 航道标注：
    - 策略 `ask`（默认）：向 answerer 询问；**没有任何 answerer 在线 → fail-closed，返回 `unavailable`**
    - 策略 `never`：一律拒绝
    - 结果四种：`allowed-once` / `rejected` / `cancelled` / `unavailable`
    - 全程留痕：`approval/asked` 与 `approval/decided` 成对写入日志
  - 气泡（哆啦A梦）：安全系统的默认值，决定了它在凌晨三点的行为。
- **技术点**：approval seam 见 `packages/interaction/user-approval/`；fail-closed 意味着「配置缺失」与「拒绝」一样安全——呼应「Misconfiguration fails loud」。

### 第 10 页 ｜ 启发页：配置即产品的分形设计
