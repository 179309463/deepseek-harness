</div>

很多人对 profile 的第一印象是「一份大配置文件」——错了。`loadProfile` 揭示真相：profile 目录的 `package.json` 里只有一个 `dsh.profile.bundles` 数组，它是**一份有序的 bundle 名单**。

- 名单的初始值来自 `PROFILE_TEMPLATES`（113-117 行）：`web` 是 `dsh-base + dsh-web-app`，`headless` 是 `dsh-base + dsh-headless`。首次使用时自动初始化。
- 每个 bundle 必须在自己的 `package.json` 里声明 `dsh.bundle.patch` 指向一个 patch 文件，**没声明就直接抛错**——「把一个不含 bundle 的包当层用」被定义为配置错误，而不是「没有 patch」。这是仓库「misconfiguration fails loud」规约的典型样本。
- 最后才读 profile 自己的 `cordis.patch.yml`——注意它排在所有 bundle 之后。

</CodeWalk>

<CodeWalk file="apps/cli/src/profile-boot.ts" lines="120-129" symbol="allPatches" title="精读 2：allPatches——四层叠加的唯一真相">

<div slot="code">

```ts

/** The full patch stack of one composed profile, in application order. */
function allPatches(composed: ComposedProfile): PatchOptions[] {
  return [
    ...composed.bundlePatches,
    ...composed.profile.patches,
    ...composed.homePatches,
    ...composed.overlays,
  ]
}
```

</div>

短短 8 行，却是整个装配体系里最需要背下来的一段。四层叠加，**数组顺序就是应用顺序，后写的赢**：

1. **profile bundles（有序）**：`dsh.profile.bundles` 里每个 bundle 的 patch 文件按名单顺序展开。`dsh-base` 永远在最底层，负责把 `agent`、`tools`、`agent-loop` 这些核心行「插入」空树。
2. **profile 自己的 `cordis.patch.yml`**：你对这个 profile 的私有改装。
3. **`$DSH_HOME/cordis.patch.yml`**：机器级偏好（比如全机器统一换模型）。它压在单 profile 层之上——机器主人的话比分身的话大。
4. **`--patch`  overlays（可重复）**：命令行临时实验，最高优先级，重启即消失。

还有一个隐藏角色：同文件 59-64 行的 `PROFILE_ROOT_CONFIG`。profile 根目录的 `cordis.yml` **每次 boot 都被重写为恒等的空数组 `[]`**。为什么？因为 Loader 的树写回机制可能把合成结果「烘焙」进根文件，导致下次启动时每个 bundle 的 insert 被重复执行。把根钉死为空，整棵树就**只能**由 patch 层插入而成——这就是「空根不是 bug 是设计」的全部原因。

</CodeWalk>

<CodeWalk file="packages/bundle/base/cordis.patch.yml" lines="6-28" symbol="dsh-base patch" title="精读 3：一份真实的 patch 层——insert 与整字段覆盖">

<div slot="code">

```yaml
# A patch replaces the targeted row's whole `config` rather than merging into
# it, so a row whose value differs by mode does NOT live here: it belongs to
# each mode bundle, keeping any single row down to one bundle layer plus the
# user's. Mode-specific rows appear below only with shared plugin identity and
# neutral defaults; each mode bundle restates its complete configuration.
#
# Row order carries no load semantics (activation is service-availability
# driven); the grouping is for readers.

- insert:
    - id: timer
      name: '@deepseek-ai/cordis-plugin-timer'

    - id: hmr
      name: '@deepseek-ai/cordis-plugin-hmr'
      config:
        root: ['.']

    - id: llm
      name: '@deepseek-ai/dsh-llm'

    - id: session
      name: '@deepseek-ai/dsh-session'
```

</div>

这是 `dsh-base` bundle 的真实 patch 文件开头，它教会我们 patch 语法的两件事：

- **`insert` 往空根里「插入」行**。每一行有稳定的 `id`（如 `session`、`agent`），后续层用同一个 `id` 就能精确命中它。整个 agent 脊椎就是 `dsh-base` 这样一行行插出来的。
- **patch 是整字段覆盖，不是 deep merge**。文件头注释写得明明白白：按 `id` 命中一行后，`config` 是**整个替换**而非递归合并。所以注释里那条架构规则才成立——随模式变化的值不住在 base 层，而是放进各自的 mode bundle 里完整重述，保证任何一行最多被「一个 bundle 层 + 用户层」碰过。

胖虎式直觉「我 patch 里只写一个键，其他键会保留吧？」——不会。少写的键就是没了。这条语义避免了「三层各改一点、最后谁也说不清最终值」的配置悬案。

</CodeWalk>

```ts
  const ctx = new Context()
  // Two failure labels: `prepare` runs before any config-tree entry mounts,
  // so its failure is host setup, not the plugin tree.
  let stage = 'host preparation failed'
  try {
    ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + '/'
    ctx.provide('dshHomePath', dshHomePath)
    await ctx.plugin(Loader)
    await prepare?.(ctx)
    stage = 'plugin tree failed to load'
    await mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)
    // A surface can finish and dispose the whole tree while startup is still
    // in flight, before the last entry settles. The Loader service goes with
    // it, and the activation audit describes a live tree — reading `ctx.loader`
    // past this point would throw a TypeError over an app that exited exactly
    // as asked. Transactional group updates settle
    // lifecycle inside the mount, so the teardown can land before it returns;
    // re-check after every await.
    await ctx.get('loader')?.await()

    await assertEntriesActivated(ctx, binName)
    return ctx
```

</div>

叠好的 patch 在这里落地。流程精确得像发射倒计时：

1. `new Context()`——第 1 章的「宇宙大爆炸」。
2. `ctx.plugin(Loader)`——先挂装载器本身。
3. `prepare?.(ctx)`——宿主的私活（命令行注入、环境快照），**在任何配置行挂载之前**跑，所以它失败算「host preparation failed」，不算插件树的锅。
4. `mountRootInclude`——以空根 `cordis.yml` 为锚点挂上 Include，四层 patch 一次性 `applyEntryPatches` 上去。
5. `loader.await()` 之后还要**再查一次** `ctx.get('loader')`——因为某个界面可能在启动途中就把整棵树 dispose 了（比如 headless 任务瞬间跑完）。注释说得很直白：每个 await 之后都要重新确认世界还在。
6. `assertEntriesActivated` 做激活审计，然后才把 `ctx` 交出去。

</CodeWalk>

模型每调一次工具，都要先过这道 `tools/pre-execute` waterfall（第 1 章讲过的洋葱链在这里第一次露出獠牙）：

- **内建 `next` 是「默认 allow」**。任何一个监听器都可以拦截：返回 `deny` 直接掐死；返回 `ask` 则升级给真人。
- `PreToolDecision` 是个封闭三态（588-591 行）：`allow` / `deny`（带 reason）/ `ask`（可选 reason）。
- `ask` 走 `serviceAsk`（1689-1729 行）转给 `ctx.get('approval')`。注意它是 **`ctx.get` 机会式消费**：没挂审批服务的部署，ask 直接降级为 deny——「此工具需要审批（尚不支持）」。
- 被拒的工具不会消失得无影无踪：拒绝原因被包装成 `Error: ...` 的工具结果**回喂给模型**。模型能读到「用户拒绝了你」，下一轮就会换策略，而不是傻乎乎重试。

这就是「plugins, not loop changes」的实战：审批策略、日志、拦截器全都是挂在 waterfall 上的普通插件，工具调度器自己一行策略都没有。

</CodeWalk>

    if (signal?.aborted) return 'cancelled'

</div>

审批服务的核心哲学一句话：**这条链上所有意外都收敛到拒绝**。看三个防御层：

- **内建 `next` 返回 `unavailable`**——没有任何 answerer（比如纯自动化环境没挂 UI 审批插件）时，结果是「无审批通道」，`serviceAsk` 把它映射成 deny。危险操作默认被拦，这叫 fail-closed。
- **answerer 抛异常 → `unavailable`**。注释很传神：「answerer 出错必须让这个问题关闭，而不是让调用方的工具调用悬着」。审批者崩溃绝不能变成放行。
- **answerer 返回词汇表外的野值 → 归一化为 `unavailable`**。连「回答得不像话」都被视为没回答。

别忘了留痕：`request()`（257-276 行）在派发前后各写一条会话事件——`approval/asked`（谁问的、问什么）与 `approval/decided`（id + 结果）。这正是第 4 章「记忆铁律」的延伸：**凡影响模型可见行为的事，必须能从会话日志重建**。而且 request 要求必须在打开的 turn 内调用，否则直接抛错——游离在 turn 之外的审计事件在崩溃恢复时是垃圾数据。

至于 `danger-full-access` 这类权限 preset（`packages/interaction/permission-presets`）：它把 `sandbox/mode: danger-full-access` 与 `approval/policy: never` 打包成一个用户可选项——适合容器里跑一次性任务、CI 无人值守的场景；日常办公请老实待在 `workspace-write + ask`。

</CodeWalk>

## 动手实验

在仓库根目录验证本章结论（需要 `DEEPSEEK_API_KEY` 的实验已标注）：

2. **验证 patch 是整字段覆盖**：写一个 `/tmp/my.patch.yml`，只给某行的 `config` 写一个键，`pnpm dsh --profile headless --patch /tmp/my.patch.yml --dump-config`，观察该行 config 里其他键**全部消失**——不是合并，是替换。
3. **验证空根铁律**（需 key）：打开 `$DSH_HOME/profiles/headless/cordis.yml` 手改内容，再跑一次 `pnpm dsh --profile headless "say hi"`，回头再看——文件已被重置为 `[]`。根不属于你，patch 层才是你的画布。

## 胖虎翻车现场

> 胖虎：「我在 cordis.patch.yml 里给 hmr 的 config 加了个键，结果热重载整个挂了——我不就加了一行吗？！」

加了「一行」= 替换**整个** config。原来的 `root: ['.']` 被你的单行 config 顶掉了，hmr 拿不到 root 自然炸。patch 的语义是「整字段覆盖」，想改一个键，请把这行的**完整 config** 抄过来再改。这也是为什么 base bundle 的注释要求「任何一行最多被一个 bundle 层碰过」——层数越少，最终值越可追溯。

> 胖虎（again）：「我把审批插件从 patch 里 disabled 了，心想模型总算能放开手脚干活，结果所有危险命令全被拒了！」

这正是 fail-closed 在保护你。没了 answerer，`approval/request` 落到内建 `unavailable`，`serviceAsk` 一律映射成 deny。想真正放开手脚，正确姿势是权限 preset：切到 `danger-full-access`（沙箱不限制 + 审批策略 `never`），而不是拆闸门——拆掉的闸门会以「全部拒绝」的方式继续站岗。

## 小结卡

- profile 是**有序的 bundle 名单**；根 `cordis.yml` 恒为空数组，整棵树由 patch 层 insert 而成。
- 四层叠加顺序：bundles → profile patch → `$DSH_HOME` patch → `--patch`；数组顺序即应用顺序，**整字段覆盖**，后写的赢。
- 工具执行前必过 `tools/pre-execute` waterfall：`allow` / `deny` / `ask` 三态，ask 升级给 `ctx.approval.request`。
- 审批链 fail-closed：无 answerer、answerer 抛错、返回野值，全部收敛到 `unavailable` → deny；`approval/asked` 与 `approval/decided` 成对留痕。
- 想放开权限用 preset（如 `danger-full-access`），别拆审批插件。
