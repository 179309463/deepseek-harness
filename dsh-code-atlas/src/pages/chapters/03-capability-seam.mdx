```ts
declare module '@deepseek-ai/cordis' {
  interface Context {
    shell: ShellExecutor
  }
}

/**
 * Abstract bash execution service. Subclass, implement the abstract methods,
 * and load the subclass as a plugin — it registers as `ctx.shell` (one
 * implementation per context; loading a second throws, which is cordis'
 * standard duplicate-service behavior).
 *
 * Implementations must honor these semantics:
 * - {@link run} rejects only for infrastructure failures. Nonzero exits,
 *   timeout kills, and abort kills resolve with a {@link ShellRunResult}.
 * - {@link start} returns immediately; no timeout applies to background
 *   processes. `done` settles at process close and never rejects; spawn
 *   failures settle as `killed` with the error on stderr.
 * - {@link ShellProcess.readOutput} is incremental: consecutive reads never
 *   repeat output. Lossy reads report truncation and available spill files.
 * - A still-running background process is stopped and awaited when its
 *   owning composition tears down. With the subprocess seam that
 *   boundary is `ctx.subprocess` disposal, so a background process survives
 *   an executor-only reload.
 */
export abstract class ShellExecutor extends Service {
  constructor(ctx: Context) {
    super(ctx, 'shell')
  }
```

</div>

seam 的第一个角色是 **Service Definition**，它同时在两个世界注册自己：

- **编译期**：`declare module '@deepseek-ai/cordis'` 给 `Context` 接口合并进一个 `shell: ShellExecutor` 属性。从此任何包了 `import type` 这个包的地方，`ctx.shell` 都有完整类型——不需要 import 任何 Provider。
- **运行期**：`ShellExecutor` 是**抽象类**而不是纯 interface。Provider 继承它时，`super(ctx, 'shell')` 会走 `Service` 基类的注册逻辑，把实例挂到服务表的 `shell` 键下。同一 context 里再挂第二个同键实现，Cordis 直接抛错——「一个组合里恰好一个 Provider」由运行时保证。

为什么不只用 interface？因为 interface 在运行时荡然无存，没法替你完成注册；抽象类把「注册动作」焊死在构造函数里，Provider 作者想忘都忘不掉。

</CodeWalk>

</div>

注意两个类型的差异：**Request 的 `workdir`/`timeoutMs`/`stdoutMaxBytes` 全部可选，Spec 里全部必填**。

这是仓库规约「Explicit &gt; implicit」的落点：调用方提交一个「还可以省略」的 Request；Provider 的 `resolve(request)` 是唯一允许做默认化和封顶的地方，产出一份「每个字段都已落定」的 Spec；`run`/`start` 只吃 Spec，**内部不允许再出现一个 `?? default`**。

好处是可观测性与可替换性：Spec 是双方签字的最终合同，日志、测试、沙箱审计看到的都是它；换一个 Provider，只需要它实现自己的 `resolve` 策略，Consumer 的调用姿势一字不改。

还有一个安全细节：`stdin`/`env`/`dshEnv` 只出现在 Request/Spec 里，**模型工具的 JSON schema 故意不暴露它们**——hooks 桥等可信进程内调用方可以写 stdin，模型只能用 heredoc。能力差异不靠隐藏文档，而靠类型与 schema 双层执行。

</CodeWalk>

<div slot="code">

```ts
  resolve(request: ShellExecRequest): ShellExecSpec {
    const timeoutMs = clampTimeout(
      request.timeoutMs,
      this.config.timeoutMs,
      this.config.maxTimeoutMs,
      'bash-local: request.timeoutMs',
    )
    const stdoutMaxBytes = request.stdoutMaxBytes ?? this.config.maxOutputBytes
    assertPositiveFinite('request.stdoutMaxBytes', stdoutMaxBytes)
    return {
      command: request.command,
      workdir: request.workdir ?? this.config.cwd ?? process.cwd(),
      timeoutMs,
      stdoutMaxBytes,
      ...request.signal ? { signal: request.signal } : {},
      // Carry stdin/ordinary env/trusted dshEnv through verbatim — optional,
      // no config default. The subprocess service owns the scrub and merge order.
      ...request.stdin !== undefined ? { stdin: request.stdin } : {},
      ...request.env !== undefined ? { env: request.env } : {},
      ...request.dshEnv !== undefined ? { dshEnv: request.dshEnv } : {},
      // Carry a sandbox policy through verbatim: this executor never
      // confines, so the field is inert here (the seam contract) — a
      // sandboxing subclass overrides resolve() to stamp its default instead.
      sandboxPolicy: request.sandboxPolicy,
    }
  }
```

</div>

`LocalBashExecutor extends ShellExecutor`，构造函数里 `super(ctx)` 一调用，`ctx.shell` 就指向它了。而 `resolve` 是「默认化全部关在这一个函数里」的样板：

- `timeoutMs`：用 `clampTimeout` 三层收敛——请求值 &gt; 配置默认 &gt; 配置上限，超限封顶而不是报错。规约「no hardcoded tunables」也在这：`120_000`、`600_000` 这些值来自 `static Config` schema，cordis.yml 可改。
- `workdir`：请求值 → `config.cwd` → `process.cwd()`，逐级兜底一次写完。
- `stdin`/`env`/`dshEnv`：原样透传，不做默认——它们没有默认值这回事。
- `sandboxPolicy`：这个执行器从不沙箱，所以字段惰性透传（注释里写明这是 seam 合同）；沙箱子类会覆写 `resolve` 盖上自己的默认策略。

`run` 只是一行 `return this.runArgv(spec, ['bash', '-c', spec.command])`；pwsh-local 换个 argv 就是另一个 Provider。真正的执行细节全部下沉到 `ctx.subprocess`——shell seam 其实是架在 subprocess seam 之上的一层语义。

</CodeWalk>

<CodeWalk file="packages/shell/bash-local/src/index.ts" lines="223-240" symbol="LocalBashExecutor.runArgv" title="精读 4：一次前台执行——deadline、spawn 与原因分类">

<div slot="code">

```ts
  protected async runArgv(spec: ShellExecSpec, argv: readonly string[]): Promise<ShellRunResult> {
    // One deadline combines timeout and upstream cancellation; disposal clears its timer.
    using d = deadline(spec.signal, spec.timeoutMs, 'BASH_TIMEOUT')
    const handle = this.ctx.subprocess.spawn(this.spawnSpec(spec, argv, spec.stdoutMaxBytes, d.signal))
    const outcome = await handle.done
    const collected = LocalBashExecutor.collected(handle)
    // Only this executor's timeout reason counts as timedOut; outer deadlines count as aborts.
    const timedOut = timeoutOf(d.signal, 'BASH_TIMEOUT') !== undefined
    const aborted = d.signal.aborted && !timedOut
    return {
      ...outcome,
      timedOut,
      aborted,
      timeoutMs: spec.timeoutMs,
      stdout: finalOutput(collected.stdout),
      stderr: finalOutput(collected.stderr),
    }
  }
```

</div>

这段里最贵的设计是「一个 deadline 融合两种取消」：`spec.signal`（调用方的 AbortSignal）和 `spec.timeoutMs`（超时）被拧成同一个 signal 交给 spawn。于是当进程被杀时，必须回答「**谁先动的手**」：

- `timeoutOf(d.signal, 'BASH_TIMEOUT')` 有值 → 是执行器自己的超时，`timedOut: true`。
- signal 中止但不是这个超时原因 → 是上游取消，`aborted: true`。
- 两者互斥（注释明说：first-cause 分类）。这个区分会一路传到模型眼前——`timedOut` 渲染成 `[timed out after Nms]`，`aborted` 在 Consumer 里直接升级成 `AbortError`。

`using d = ...` 是显式资源管理：函数返回即清掉定时器。输出侧，stdout/stderr 经 collect 读取器收口，超预算的部分落 spill 文件，`finalOutput` 投影成 `text + truncated + spillPath`。

</CodeWalk>

## 动手实验

在仓库根目录验证本章结论（需要 `DEEPSEEK_API_KEY` 的实验已标注）：

1. **非零 exit 不炸工具**（需 key）：`pnpm dsh --profile headless "运行 exit 3，然后告诉我你观察到了什么"`。模型会收到带 `[exit code: 3]` 标记的正常结果并继续推理，而不是看到工具报错。
2. **换 Provider 不动 Consumer**：读 `packages/shell/pwsh-local/src/index.ts` 的 `argv()`（218-219 行）——同一个 Spec，只是换成 `pwsh -Command`。cordis.yml 里把 bash-local 换成它，`tool-bash` 一行不用改；但如果两个同时挂载，会在重复的 `shell` 服务注册处当场抛错。
3. **追一次完整链路**：`pnpm dsh --profile headless "列出当前目录文件"`，然后在 session 日志里找 `tool/call` 与 `tool/result` 两个事件——模型可见的一切都能从日志重建。
4. **看 seam 的全家福**：对照 `packages/compaction/compaction/src/index.ts` 和 `packages/llm/llm/src/index.ts`，注意 LLM 把 Definition 与 registry 折叠进了一个包——seam 允许折叠，但三角关系不变。

## 胖虎翻车现场

> 胖虎：「我写了 try/catch 包住 bash 工具，准备捕获 exit code 1……为什么 catch 从来进不去？」

因为非零退出根本不会走到 error 通道。`run` 的合同写得很清楚：非零退出、超时被杀、abort 被杀都以 `ShellRunResult` 正常 resolve，只有 spawn 失败这类基础设施故障才 reject。想判断命令成败，去读结果里的 `exitCode`——或者从模型视角，读文本尾的 `[exit code: N]` 标记。把「命令失败」当「工具故障」是对这个 seam 最常见的误读。

> 胖虎的另一道菜：「我直接在 Consumer 里 `import { LocalBashExecutor } from 'dsh-bash-local'`，省得走 seam！」——恭喜你把三角焊死成了直线。Provider 与 Consumer 之间禁止依赖：Consumer 只 import Definition 的类型，`inject: ['shell']` 声明运行时需求。可选服务用 `ctx.get('shell')`；已声明 inject 的才用 `ctx.shell`。这层纪律就是「明天把 bash 换成 pwsh、把本地换成分箱沙箱」时不用改 Consumer 的全部理由。

## 小结卡

- seam 是 **Definition / Provider / Consumer 三角的合称**，单个角色不构成 seam；依赖方向是 Provider→Definition←Consumer，Provider 与 Consumer 之间没有边。
- Definition 用 `declare module` 扩编译期类型，用抽象类的 `super(ctx, key)` 完成运行期注册；同键重复注册即抛错。
- **Request → Spec 显式拆分**：`resolve` 独占默认化与封顶，`run`/`start` 只吃 Spec，内部不再有隐藏默认值。
- 一次 bash 调用：model tool_call → tools/pre-execute waterfall → tool-bash.execute → `ctx.shell.resolve + run` → `ctx.subprocess.spawn` → render → session tool/result。
- **非零 exit code 不是 tool error**，是 `[exit code: N]` 标记；只有 aborted 升级成 `AbortError`。
